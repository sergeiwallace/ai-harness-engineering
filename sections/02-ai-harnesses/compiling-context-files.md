# Compiling context files

As of 2026-11-09. A sub-topic of [Harness context files]({{ '/sections/02-ai-harnesses/context-files.html' | relative_url }}), in [AI harnesses]({{ '/sections/02-ai-harnesses/' | relative_url }}).

Once you use more than one tool, or more than one machine, hand-editing each context file stops scaling. Compiling means keeping the rules in small source modules and building every tool's context file from them.

## The problem it solves

### Several tools, one set of rules

Claude Code reads `CLAUDE.md`, Codex reads `AGENTS.md`, Gemini CLI reads `GEMINI.md`. Most rules apply to all three. Three hand-kept copies drift within weeks: a fix lands in one and not the others.

### Several machines, small differences

A laptop, a cloud dev box and a work machine share most rules and differ in a few: which tools exist, what needs approval, how credentials work. Copies per machine drift the same way.

### Source modules

Each module is one Markdown file about one subject: collaboration style, git workflow, test requirements, delegation. A module can hold variants for tools that need different wording, such as the name of the sub-agent tool.

### The build

A small script reads a manifest that lists the modules in order, picks the variant for each target tool, appends the overlay for the target machine, and writes the output files. The outputs carry a header saying they are generated and naming the source folder.

```markdown
# Shared context (generated)

> DO NOT EDIT this file. Edit the source modules, then run the build
> and the installer. Edits to this file are lost at the next build.
```

### The size check

The build ends with the [size budget]({{ '/sections/02-ai-harnesses/context-file-budgets.html' | relative_url }}) check. A warn result passes and schedules a trim; a fail result stops the install.

### The install

The installer places the outputs where each tool reads them. In my harness the installer writes each build into a numbered generation folder and points the live files at it, so a bad build can be rolled back to the previous generation with one command.

## A worked example

### Adding a rule

1. Write the rule in the module it belongs to, for example the git module.
2. Run the build. It regenerates all three tool files and every machine's variant.
3. The size check reports the new total against the budget.
4. Commit the module change and the regenerated outputs together.
5. Run the installer on each machine.

### What can go wrong

| Mistake | What happens | Guard |
|---|---|---|
| Editing the generated file | the edit is lost at the next build | generated header, a check that outputs match sources |
| Building but not installing | sessions keep reading the old rules | install step in the release checklist |
| Installing from an unmerged branch | live files point at work in progress | installer refuses to link into a temporary worktree |

<details markdown="1">
<summary>The temporary worktree trap</summary>

Agents in my harness each work in their own git worktree. An installer run from one of them once linked the live context files into that worktree, which was deleted when the agent finished, and every session lost its context file. The installer now re-roots itself to the main checkout before it does anything, and a test pins that no live link ever points into a temporary worktree.

</details>

## When not to compile

One tool on one machine needs no build. Start with a hand-written file. Compile when you find yourself making the same edit in two places.
