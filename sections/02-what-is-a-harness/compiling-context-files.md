# Compiling context files

Once you use more than one tool, or more than one machine, hand-editing each context file stops scaling. Compiling means keeping the rules in small source modules and building every tool's context file from them.

## The problem it solves

### Several tools, one set of rules

| Tool | Reads |
|---|---|
| Claude Code | `CLAUDE.md` |
| Codex | `AGENTS.md` |
| Gemini CLI | `GEMINI.md` |

Most rules apply to all three. Three hand-kept copies drift within weeks: a fix lands in one and not the others.

### Several machines, small differences

A laptop, a cloud dev box and a work machine share most rules and differ in a few.

- Which tools are installed.
- Which actions need approval there.
- How credentials and network access work.

Copies per machine drift the same way as copies per tool.

### Source modules

Each module is one Markdown file about one subject.

```text
session-config/
  manifest.yaml        module order, per tool and per machine
  modules/
    collaboration.md
    git-workflow.md
    testing.md
    delegation.md
  overlays/
    laptop.md
    cloud-dev.md
```

A module can hold variants for tools that need different wording, such as the name of the sub-agent tool.

### The build

A small script reads a manifest that lists the modules in order, picks the variant for each target tool, appends the overlay for the target machine, and writes the output files. The outputs carry a header saying they are generated and naming the source folder.

```markdown
# Shared context (generated)

> DO NOT EDIT this file. Edit the source modules, then run the build
> and the installer. Edits to this file are lost at the next build.
```

### The size check

The build ends with the [size budget]({{ '/sections/02-what-is-a-harness/context-file-budgets.html' | relative_url }}) check.

| Result | Effect |
|---|---|
| pass | install continues |
| warn | install continues; a trim is scheduled |
| fail | install stops until something is trimmed or moved |

### The install

The installer places the outputs where each tool reads them.

1. It writes each build into a new numbered generation folder.
2. It points the live files at that generation.
3. A bad build is rolled back to the previous generation with one command.
4. It refuses to run from a temporary worktree, so live files always come from merged work.
5. After it runs, a live session confirms the result: `/memory` or `/context all` in Claude Code lists the files that actually loaded.

### The drift check

A test in CI rebuilds the outputs and fails if they differ from what is committed, so a hand edit to a generated file cannot land.

```text
$ build-context --check
drift: AGENTS.md differs from a fresh build (line 214)
edit the source module, then rebuild; generated files are not edited by hand
```

This is the [systems approach]({{ '/sections/02-what-is-a-harness/' | relative_url }}#a-systems-approach-to-harness-engineering) applied to the context files themselves: the generated header asks, and the check enforces.

## A worked example

### Adding a rule

1. Write the rule in the module it belongs to, for example the git module.
2. Run the build. It regenerates all three tool files and every machine's variant.
3. The size check reports the new total against the budget.
4. Commit the module change and the regenerated outputs together.
5. Run the installer on each machine.

### What can go wrong

| Mistake | What happens | Guard |
|---|---|---|
| Editing the generated file | the edit is lost at the next build | generated header, a check that outputs match sources |
| Building but not installing | sessions keep reading the old rules | install step in the release checklist |
| Installing from an unmerged branch | live files point at work in progress | installer refuses to link into a temporary worktree |

<details markdown="1">
<summary>The temporary worktree trap</summary>

Agents in my harness each work in their own git worktree.

- An installer run from one of them once linked the live context files into that worktree, which was deleted when the agent finished, and every session lost its context file.
- The installer now re-roots itself to the main checkout before it does anything, and a test pins that no live link ever points into a temporary worktree.

</details>

## When not to compile

A compile step is machinery to maintain. The tools now offer simpler ways to share text, so try these first.

| Situation | Start with |
|---|---|
| one tool, one machine | a hand-written file |
| Claude Code and Codex, same rules | an `AGENTS.md`, and a `CLAUDE.md` whose only line is `@AGENTS.md` |
| the same rules in several projects | `~/.claude/rules/` for yourself, or a `.claude/rules/` folder of symlinks to a shared folder |
| the same edit made in two places twice | a compile step |
| several machines with real differences | a compile step with overlays |
